# 按现象排查

先确定失败在提交机、平台调度还是任务容器，再检查该层的输入。
下面提炼自 2026 年 6—7 月实践，CLI 的 PATH 与命令名称于 2026-09-19 复核。
旧项目性能数字和环境补丁不作为新项目默认值。

| 现象 | 先检查 | 处理方向 |
|---|---|---|
| `volc` 存在但找不到 `mlp` | 非交互 SSH 的 PATH | 把实际 CLI 安装目录加入 PATH，见 [cli.md](cli.md) |
| YAML 被拒绝 | 当前工具版本、原生模板、字段类型、队列和存储权限 | 区分 CLI 输入和 API 响应；不要用别名猜字段 |
| list 没有刚结束的任务 | 默认状态筛选 | 查询精确 ID，或显式包括终态；不立即重复提交 |
| 一直 Queue | 队列配额、请求规格、优先级、其他排队任务 | 平台可见空卡不等于本任务可调度；不自行提高到无权限的优先级 |
| 拉镜像失败 | URL、地域、仓库权限、镜像是否存在 | 在项目范围修正镜像或认证，避免改公共镜像标签 |
| 挂载不存在/拒绝访问 | 文件系统 ID、源子目录、容器路径、当前授权 | 先明确各路径的含义，见 [任务挂载](custom-tasks.md) |
| 开发机正常、任务找不到环境 | 任务解释器、挂载路径、镜像内容 | 使用实际解释器绝对路径；不要静默切到系统 Python |
| import 到旧代码 | 模块 `__file__`、镜像内 PYTHONPATH、安装位置 | 修正项目安装和环境；不靠额外 PYTHONPATH 拼接掩盖问题 |
| 在线日志服务启动失败 | 任务内网络与私密认证可用性 | 项目明确选择在线或离线模式；不自动降级后丢失实验记录 |
| 多 rank 抢删输出目录 | 所有进程是否同时初始化/清空目录 | 指定进程负责共享目录操作；按框架同步，不吞异常 |
| 未训练就显存占满 | 辅助脚本是否初始化了 GPU 框架并预分配 | CPU 工作显式不暴露 GPU；训练按所用框架配置，避免误伤共享任务 |
| CUDA import 成功但首次运算失败 | 实际框架构建、宿主驱动、加载的 CUDA 库 | 最小真实 kernel 复现；采用相容组合，不盲加 compat 路径 |
| 单机正常，多机卡住 | worker 数、rank、主节点地址/端口、网络与 NCCL 日志 | 两节点最小通信测试；RDMA 设备可见不等于路径可用 |
| DataLoader 慢/小文件读取异常 | 实际数据是否从 TOS 挂载读取、吞吐与 CPU 限额 | 少量数据预热 vePFS 对比，按测量定位 |
| tosutil 访问失败或慢 | 地域、endpoint、网络路径、源/目标层级 | 区分公网/内网和 TOS/S3 endpoint，先用小样本验证 |
| 自动重试但进度归零 | 入口是否真的加载了完整 checkpoint | 恢复状态由训练程序负责，见 [恢复说明](custom-tasks.md) |

排查时保留第一个完整 traceback、任务 ID、实例 ID、实际命令和必要配置。
不把完整终端记录、整个环境变量列表或所有账户任务输出堆入知识库。
修复后只将能迁移的“现象—原因—处理—适用条件”写回本页；具体运行结果归项目。

观察多卡性能时同时记录每卡 batch、全局 batch、步数与样本数。
更多卡不一定缩短固定步数训练；吞吐提升和训练等价性是不同问题。
不要把某次旧案例的倍数写成平台性能保证。

## Zenith 提交载荷与创建502

2026-10-12 的项目实测表明：当启动入口通过环境变量携带较大的代码包，
缩小无损传输载荷是值得验证的修复方向。OpenWAM 和 DreamVLA 在保持原代码与科学配置后，
将原 tar 内容改用 BZ2 传输，后续创建成功。两例均未取得服务端根因，
因此不能把成功归因写成已确认的平台限制，也不能声称存在 128 KiB 总请求上限。
同日另一个执行任务将载荷从约159 KB降至106 KB后仍返回502，后续错误指向存储准备。
**先定位失败阶段，再决定是否调整载荷；HTTP状态码相同不代表原因相同。**

### 先分清哪一层失败

| 已观察的证据 | 能判断什么 | 下一步 |
|---|---|---|
| 客户端构造/语法/schema检查失败 | 尚未进入有效创建 | 修复准确字段、引号或封装，不排GPU诊断 |
| 创建 operation FAILED/502，没有 JOB ID、没有原生输出 | 尚无任务执行证据；底层资源是否创建仍可能未知 | 按原幂等键与 operation 查询；有阶段信息时检查 provider、存储或创建命令的实际错误 |
| 错误明确在存储准备/挂载阶段 | 失败在代码执行之前 | 核对实际授权、选中的挂载与必要路径；压缩代码不能证明挂载已修复 |
| JOB已创建，但 replica/default日志空或pending | 缺运行证据 | 同一观察器继续原查询；用已有授权的只读通路核对真实产物，不重复提交 |
| 容器内出现解包/import/训练 traceback | 已进入任务代码 | 修复首个真实异常，保留原代码版本和完整恢复点 |

准入 allowed、HTTP202、创建成功、RUNNING、GPU利用率分别只说明各自阶段。
都不能替代实际 rank 恢复、optimizer更新、完整checkpoint和阶段退出记录。

### 只改变传输封装

测量实际发送的请求，而不只比较归档文件：环境变量数量、每个值的 UTF-8 字节数、
环境变量值总量、entrypoint字节数和最终序列化body字节数。Base64会扩大压缩结果；
更短的entrypoint并不保证总body更小。字段限制以当前接口为准，不从单次成功反推官方上限。

本次 OpenWAM 对照中，原 tar 为430080 B、48个成员。gzip传输92651 B改为BZ2传输69365 B，
环境变量值总量124429 B降至93381 B，compact JSON body从131598 B降至100369 B，
而entrypoint几乎不变。DreamVLA同样保持74个原成员及tar metadata，
gzip107467 B改为BZ2 78713 B后创建成功。这些是各自案例的测量，不是新任务的容量保证。

封装顺序可以保留已发布的原归档，先取出原 tar，再压缩传输；不要把压缩格式变化混进源码修改：

```python
raw_tar = gzip.decompress(original_archive_bytes)
wire = bz2.compress(raw_tar, compresslevel=9)
assert bz2.decompress(wire) == raw_tar
encoded = base64.b64encode(wire).decode("ascii")
```

接收端明确按BZ2解包，格式不符时显式失败；不静默尝试多个格式。
环境变量分块按实际接口边界生成连续编号，并在本地重组实际env后核对原 tar。
如果内嵌仍不合适，可使用已有授权存储中的小入口；先真实读回代码与路径，
不要为了缩body擅自增加存储权限、启动DEV或替换训练来源。

### 提交前的必要检查与重试边界

1. 解压前后逐字节核对原 tar；核对成员路径、类型、文件内容、权限和必要metadata。
   tar路径不得绝对化或逃出目标目录。保持模型、seed、world/global batch、optimizer、scheduler、
   数据与采样/RNG合同，不通过删训练代码或缩预算换取创建成功。
2. 对实际entrypoint做Python/Bash语法检查，并本地执行解包；多节点共享部署时验证一次并发、
   相同载荷重复部署和不同载荷冲突拒绝。临时文件写完后原子发布到新的代码版本目录，
   不覆盖健康JOB正在使用的版本。Windows检查不能冒充Linux权限或真实JOB部署验收。
3. 保留旧request、幂等键、原提交时间和operation。未知POST只用原键查询，
   完整任务列表没有名称也不能单独证明底层资源不存在。明确失败并处理重复资源风险后，
   才按项目已有授权生成独立新attempt；不要改原键重POST或改写旧时间。
4. 新创建仍需原生验收。将实际退出码、rank恢复/保存、optimizer进度与必要输出持久保存；
   默认日志为空时不能由CPU结构检查或平台终态合成缺失事件。健康任务无需为采用更小封装重启。

上述封装往返、并发/重复部署、冲突和语法检查在OpenWAM本地实测通过；
后续实际GPU producer的32 rank恢复与optimizer进度有独立记录。
这证明该候选可用，未证明此前502的原因，也未证明整程训练已经完成。
具体请求、operation、测量及验收仍由使用方 SE3-WAM 项目的
`docs/experiments/BASE1/results/openwam_pro6000_fresh_20261011.json` 和
`dreamvla_pro6000_training_20261011.json` 拥有；本节只维护通用排查与适用边界。
