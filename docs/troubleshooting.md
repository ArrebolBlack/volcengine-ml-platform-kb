# 按现象排查

先确定失败在提交机、平台调度还是任务容器，再检查该层的输入。
下面提炼自 2026 年 6—7 月实践，CLI 的 PATH 与命令名称于 2026-09-19 复核。
旧项目性能数字和环境补丁不作为新项目默认值。

| 现象 | 先检查 | 处理方向 |
|---|---|---|
| `volc` 存在但找不到 `mlp` | 非交互 SSH 的 PATH | 把实际 CLI 安装目录加入 PATH，见 [cli.md](cli.md) |
| YAML 被拒绝 | 当前工具版本、原生模板、字段类型、队列和存储权限 | 区分 CLI 输入和 API 响应；不要用别名猜字段 |
| list 没有刚结束的任务 | 默认状态筛选 | 查询精确 ID，或显式包括终态；不立即重复提交 |
| 一直 Queue | 队列配额、请求规格、优先级、其他排队任务 | 平台可见空卡不等于本任务可调度；不自行提高到无权限的优先级 |
| 拉镜像失败 | URL、地域、仓库权限、镜像是否存在 | 在项目范围修正镜像或认证，避免改公共镜像标签 |
| 挂载不存在/拒绝访问 | 文件系统 ID、源子目录、容器路径、当前授权 | 先明确各路径的含义，见 [任务挂载](custom-tasks.md) |
| 开发机正常、任务找不到环境 | 任务解释器、挂载路径、镜像内容 | 使用实际解释器绝对路径；不要静默切到系统 Python |
| import 到旧代码 | 模块 `__file__`、镜像内 PYTHONPATH、安装位置 | 修正项目安装和环境；不靠额外 PYTHONPATH 拼接掩盖问题 |
| 在线日志服务启动失败 | 任务内网络与私密认证可用性 | 项目明确选择在线或离线模式；不自动降级后丢失实验记录 |
| 多 rank 抢删输出目录 | 所有进程是否同时初始化/清空目录 | 指定进程负责共享目录操作；按框架同步，不吞异常 |
| 未训练就显存占满 | 辅助脚本是否初始化了 GPU 框架并预分配 | CPU 工作显式不暴露 GPU；训练按所用框架配置，避免误伤共享任务 |
| CUDA import 成功但首次运算失败 | 实际框架构建、宿主驱动、加载的 CUDA 库 | 最小真实 kernel 复现；采用相容组合，不盲加 compat 路径 |
| 单机正常，多机卡住 | worker 数、rank、主节点地址/端口、网络与 NCCL 日志 | 两节点最小通信测试；RDMA 设备可见不等于路径可用 |
| DataLoader 慢/小文件读取异常 | 实际数据是否从 TOS 挂载读取、吞吐与 CPU 限额 | 少量数据预热 vePFS 对比，按测量定位 |
| tosutil 访问失败或慢 | 地域、endpoint、网络路径、源/目标层级 | 区分公网/内网和 TOS/S3 endpoint，先用小样本验证 |
| 自动重试但进度归零 | 入口是否真的加载了完整 checkpoint | 恢复状态由训练程序负责，见 [恢复说明](custom-tasks.md) |

排查时保留第一个完整 traceback、任务 ID、实例 ID、实际命令和必要配置。
不把完整终端记录、整个环境变量列表或所有账户任务输出堆入知识库。
修复后只将能迁移的“现象—原因—处理—适用条件”写回本页；具体运行结果归项目。

观察多卡性能时同时记录每卡 batch、全局 batch、步数与样本数。
更多卡不一定缩短固定步数训练；吞吐提升和训练等价性是不同问题。
不要把某次旧案例的倍数写成平台性能保证。
